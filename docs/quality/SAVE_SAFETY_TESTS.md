> **Validation status of every test in this file: Not run.** No persistence code exists, and the storage mechanism is
> undecided (OPEN-006, [ADR-0003](../architecture/decisions/ADR-0003-career-save-isolation.md) Proposed).

## 1. Purpose

These tests protect the most damaging failure modes of the project: corrupted cities or career data, money or progress
leaking from a newer session into an older save, duplicated rewards, and saves that no longer load after the mod is
removed (RISK-005, RISK-006, RISK-017). They define the primary test for each `REQ-SAVE-*` requirement and additional
tests for the hazards around them.

They are also the yardstick for the PHASE-01 persistence spike: each storage option under evaluation (In-save,
Sidecar, Hybrid) is run against the same tests before ADR-0003 is decided (§4).

## 2. Safety rules for running these tests

1. **Lab copies only.** Every test uses fresh working copies of lab saves ([TEST_STRATEGY](TEST_STRATEGY.md) §5).
   Primary saves are never opened, copied over, or used as fixtures (RISK-028). If a sidecar store is used, its
   location must also be a lab location.
2. **Fault injection only by an approved method.** Forced termination, full or read-only storage, and corrupted data
   are applied only with a method the project owner has approved (OPEN-506), only to lab copies, and only on storage
   designated for testing. Never manipulate system folders, the game installation, or storage that holds other data.
3. **Hash before and after.** Record a content hash of every lab save, career record, and last valid copy before the
   test and after each step that should not change them.
4. **Keep, don't delete, evidence of failure.** Quarantined or corrupted data that reveals a defect is kept in the
   git-ignored `artifacts/` area and referenced from the run. It is never committed (it may contain game data).
5. **Synthetic fixtures for logic tests.** Logic-layer fixtures are generated by the future logic test project from
   the schema. They are never extracted from player saves.
6. **Stop on surprise writes.** If anything outside the lab scope is written, or the game version changes, suspend the
   run ([TEST_STRATEGY](TEST_STRATEGY.md) §9).

## 3. Abstract contract under test

The storage mechanism is pending (OPEN-006). Procedures are therefore written against the abstract contract in
[SPEC-SAVE](../architecture/SAVE_FORMAT.md), not against a particular hook or file layout:

| Term | Meaning in these tests |
|---|---|
| **City save** | The game's own save file for a lab city. |
| **Career record** | The persisted career data bound to one save identity, wherever it is stored (In-save, Sidecar, or Hybrid). |
| **Save identity** | City identity + career profile ID + save revision ID, plus the schema version. |
| **Last valid copy** | The most recent career record that passed validation. Never overwritten by invalid data. |
| **Quarantine** | Where invalid persisted data is isolated for diagnosis without being loaded or deleted. |
| **Persistence readout** | A planned Diagnostics report showing the loaded save identity, schema version, validation result, last-valid-copy status, and quarantine contents (OPEN-502). |
| **Restart** | Closing the game completely and starting it again, as opposed to loading another save within the session. |

**Save invariants** checked after every load in every test:

| Invariant | Statement |
|---|---|
| I1 | The career data shown belongs to the loaded save identity: no data from another revision, city, or profile. |
| I2 | The wallet equals the ledger sum, and TransactionIds are unique. |
| I3 | Every mod entity is registered; no orphans; no duplicated career vehicles, passengers, or cargo. |
| I4 | The last valid copy is intact (its hash changes only when a newer valid save replaces it as SPEC-SAVE defines). |
| I5 | The city loads, and its structural state is unchanged by the mod's persistence. |
| I6 | Quarantine holds exactly the invalid data, and the event is logged and reported to the player. |

## 4. Storage-option variants

Each test applies to every storage option. The points where the options differ, and must be exercised specifically,
are:

| Concern | In-save | Sidecar (revision-bound) | Hybrid |
|---|---|---|---|
| Revision binding (TEST-SAVE-001, 101, 107) | Data travels inside the city save; check that older saves really contain older data. | The career record is located by save identity; check the lookup rules, including copied saves that share a revision ID. | Check both paths and their agreement. |
| Write ordering (TEST-SAVE-102, 111) | A termination during the game's save write affects city and career data together. | Two separate writes; the order and the commit marker decide what survives. | Both. |
| Storage failure (TEST-SAVE-103) | The failure surfaces through the game's save. | The sidecar write can fail while the city save succeeds. | Both. |
| Mod removed (TEST-SAVE-006, 108) | Behavior of mod data inside a save loaded without the mod must be observed. **[Documented upstream]** A community reference states that removing a mod drops its components and keeps the city ([SOURCES](../research/SOURCES.md)); unverified by us. | The sidecar remains on disk; orphan handling and cleanup must be checked. | Both. |

**PHASE-01 comparison set [Proposal]:** run TEST-SAVE-001, 004, 006, 101, 102, 107, and 111 against each option
prototyped in the persistence spike, and attach the runs to ADR-0003.

## 6. Test definitions

The setups named in preconditions (Logic harness, Lab, Career lab, Control copy) are defined in
[TEST_SCENARIOS](TEST_SCENARIOS.md) §3.

Before careers exist (PHASE-01), "career data" means the minimal test record that the save foundation persists (for
example a test wallet value and one stable reference), as defined in SPEC-SAVE. From PHASE-06 on, the full career data
is used.

### 6.1 Primary tests

#### TEST-SAVE-001 — An older save never shows data from a newer session
- **Layer:** Logic + Integration · **Requirement:** REQ-SAVE-001 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Logic harness for the identity-binding rules; Career lab; persistence readout.
- **Procedure:** 1) Logic: look up career records by save identity with exact matches, a different revision, a different city, and a different profile. 2) In-game: load the lab city, set career state A, save as S1. 3) Change to state B, save as a new save S2. 4) Change to state C without saving. 5) Load S1 and inspect wallet, ledger, vehicles, and progress. 6) Load S2 and inspect. 7) Restart and repeat steps 5–6.
- **Expected result:** Logic: only an exact identity match returns a record; a mismatch follows SPEC-SAVE and never yields a newer revision's data. In-game: S1 shows exactly state A and S2 exactly state B. State C appears nowhere. Invariants I1–I5 hold after every load.

#### TEST-SAVE-002 — Schema version, forward migration, and refusal of an unknown newer schema
- **Layer:** Logic + Integration · **Requirement:** REQ-SAVE-002 · **Phase:** PHASE-01, PHASE-12 · **Validation status:** Not run
- **Preconditions:** Logic harness with synthetic records at schema N−1, N, and N+1 (N = current); in-game fixtures once more than one schema version exists.
- **Procedure:** 1) Serialize a record and check that it carries schema version N. 2) Deserialize the N−1 record and compare it with the expected migrated record. 3) Deserialize the N+1 record. 4) In-game, run TEST-SAVE-105 and TEST-SAVE-106 when their fixtures exist.
- **Expected result:** Every record carries its schema version. N−1 migrates to N exactly as the migration rules in SPEC-SAVE define. N+1 is refused, its bytes are unchanged, and the refusal is reported. No data is lost in any case.

#### TEST-SAVE-003 — Stable identifiers, revalidated on load
- **Layer:** Logic + Integration · **Requirement:** REQ-SAVE-003 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Logic harness; Career lab with persisted references (a parked career vehicle, a home base or test building, an access point).
- **Procedure:** 1) Logic: serialize a record and check that every reference uses the stable identifier form SPEC-SAVE defines and that no raw runtime entity ID is stored. 2) In-game: save; restart; load; check that every reference resolves to the same object. 3) Demolish a referenced building in `Building`, save, restart, and load.
- **Expected result:** References resolve to the same objects across a restart. A reference whose target no longer exists is detected on load and handled as SPEC-SAVE / SPEC-ENTITY define (fallback or invalidation). A reference is never bound to an unrelated entity that happens to reuse a runtime ID.

#### TEST-SAVE-004 — Atomic writes, quarantine, and the last valid copy
- **Layer:** Logic + Integration · **Requirement:** REQ-SAVE-004 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Logic harness for the validation and quarantine decision; Career lab; persistence readout; an approved method to place an invalid record in a lab copy (OPEN-506).
- **Procedure:** 1) Create valid save S1 and record the last valid copy's hash. 2) Logic: feed invalid records to the load validator. 3) In-game: replace the career record in a copy of S1 with an invalid one and load it. 4) Play briefly and save. 5) Restart and load S1's untouched copy.
- **Expected result:** Invalid data is quarantined, neither loaded nor deleted, and the player is informed (I6). The last valid copy keeps its hash and remains loadable (I4). The save in step 4 never overwrites the last valid copy with invalid data. Write atomicity is exercised in TEST-SAVE-102, 103, and 111.

#### TEST-SAVE-005 — Save and load during an active taxi mission
- **Layer:** Integration · **Requirement:** REQ-SAVE-005 · **Phase:** PHASE-06 · **Validation status:** Not run
- **Preconditions:** Career lab with the taxi career; ledger and registry readouts.
- **Procedure:** For each point: fare accepted but not started; driving to the pickup; passenger boarding; driving to the destination; immediately after payment: 1) save; 2) load within the session; 3) restart and load.
- **Expected result:** The mission either resumes in a consistent state or resolves safely as SPEC-SAVE / SPEC-MISSION define. No reward is duplicated (ledger), and no passenger, vehicle, or marker is lost or orphaned. Invariants I1–I3 hold.

#### TEST-SAVE-006 — Mod disabled or removed: the city stays loadable (clean exit)
- **Layer:** Integration · **Requirement:** REQ-SAVE-006 · **Phase:** PHASE-01, PHASE-13 · **Validation status:** Not run
- **Preconditions:** Lab with the isolated mod set; a lab save S1 created with the mod in use (career record, a parked career vehicle, mod entities); a Control copy saved without the mod.
- **Procedure:** 1) Disable the mod in the isolated mod set; load S1; inspect the city and any leftover mod objects; save as S1-off. 2) Remove the mod's files from the lab mod set; load S1 and S1-off. 3) Compare structural city state with the Control copy.
- **Expected result:** The city loads in every case, and no city data is lost. What remains of mod data (leftover objects, ignored data, sidecar files) is observed and documented. The documented clean-exit procedure in [INSTALL_UPGRADE_UNINSTALL](../release/INSTALL_UPGRADE_UNINSTALL.md) is updated from this evidence. No safe-uninstall claim is made before this test passes (REQ-REL-002).

### 6.2 Additional tests

#### TEST-SAVE-101 — Branching save timeline
- **Layer:** Integration · **Requirement:** REQ-SAVE-001 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Career lab; persistence readout.
- **Procedure:** 1) Save S1, play, save S2, play, save S3. 2) Load S1, play differently, save S1b. 3) Load S3, S2, and S1b in turn. 4) Overwrite S2's slot from S1b's timeline and load it.
- **Expected result:** Each load shows exactly its own branch. S1b never contains S2 or S3 data, and S3 never contains S1b data. Overwriting a slot creates a new save revision as SPEC-SAVE defines. I1–I4 hold.

#### TEST-SAVE-102 — Forced termination during a write (simulated, lab only)
- **Layer:** Integration · **Requirement:** REQ-SAVE-004 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Career lab with a valid last valid copy; an owner-approved termination method (OPEN-506).
- **Procedure:** Terminate the game at each point: before the career write starts, in the middle of it, and during the city save write (for the point between the two writes, see TEST-SAVE-111). After each: restart and load the most recent save and the previous one.
- **Expected result:** On restart, either the complete previous state or the complete new state loads. A partial career record is never loaded; it is quarantined (I6). The last valid copy is intact (I4). If the game's own city save is damaged by the termination, that observation is recorded as host-game behavior, and our data must not make the outcome worse.

#### TEST-SAVE-103 — Full or read-only storage
- **Layer:** Integration · **Requirement:** REQ-SAVE-004 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Career lab on storage designated for testing; an owner-approved method to fill it or make it read-only (OPEN-506).
- **Procedure:** 1) Fill the storage so that the next write fails; save. 2) Restore space; make the location read-only; save. 3) Restore write access; save; restart; load.
- **Expected result:** Each failed write is detected and the player is informed. No partial data is left behind, the last valid copy is intact, and the game remains stable. After access is restored, saving works normally.

#### TEST-SAVE-104 — Corrupted data variants are quarantined
- **Layer:** Logic + Integration · **Requirement:** REQ-SAVE-004, REQ-SAVE-003 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Logic harness; Career lab; persistence readout; an approved method to place records in lab copies (OPEN-506).
- **Procedure:** For each variant, load it in the Logic harness and in a lab copy: a truncated record; random byte changes; a structurally valid record with invalid values (for example a negative capacity or an unknown enum value); a ledger with duplicate TransactionIds; a wallet that differs from the ledger sum; a record carrying another city's or revision's identity; an empty record.
- **Expected result:** Every variant is detected and quarantined with a logged reason (I6). The behavior SPEC-SAVE defines for the case follows (use of the last valid copy, or a documented recovery), and the player is informed. Nothing is silently "repaired" in a way that creates money or progress. Quarantined data remains available for diagnosis.

#### TEST-SAVE-105 — Unknown newer schema refused in-game without data loss
- **Layer:** Integration · **Requirement:** REQ-SAVE-002 · **Phase:** PHASE-01, PHASE-12 · **Validation status:** Not run
- **Preconditions:** Lab; a lab save whose career record has schema N+1 (from a newer development build, or synthetic); the current build at schema N.
- **Procedure:** 1) Load the save with the current build. 2) Play briefly and save the city. 3) Load the original save again with the newer build.
- **Expected result:** The career record is refused and not modified, and the player is informed. The game does not crash. The city loads, or the load is refused, as SPEC-SAVE defines. Saving with the older build never destroys or downgrades the newer record: step 3 shows the newer data intact.

#### TEST-SAVE-106 — Migration from every prior schema version
- **Layer:** Logic + Integration · **Requirement:** REQ-SAVE-002 · **Phase:** PHASE-12 and every schema change · **Validation status:** Not run
- **Preconditions:** A frozen lab fixture for every prior schema version, created by the build that introduced it, with its expected migrated snapshot.
- **Procedure:** 1) Load each fixture with the current build. 2) Compare the migrated data with the expected snapshot. 3) Save, restart, and load again.
- **Expected result:** Every prior schema migrates to the current one through the tested path, with values preserved as the migration rules define. A second load does not migrate again. The pre-migration data stays recoverable as SPEC-SAVE defines.

#### TEST-SAVE-107 — Duplicate load of the same save; copied saves
- **Layer:** Integration · **Requirement:** REQ-SAVE-001 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Career lab; persistence readout.
- **Procedure:** 1) Load S1, play without saving, load S1 again. 2) Make a copy S1-copy of S1 (through the game's interface if it offers one, otherwise as a lab file copy). 3) Load S1, play, and save over S1. 4) Load S1-copy. 5) Load the new S1.
- **Expected result:** Step 1 shows S1's saved state; unsaved changes are discarded. S1-copy shows the state at copy time and never the later S1 data. Any ambiguity from two saves sharing one origin is detected and handled as SPEC-SAVE defines. I1–I4 hold.

#### TEST-SAVE-108 — Sessions without the mod, then re-enabling it
- **Layer:** Integration · **Requirement:** REQ-SAVE-006, REQ-SAVE-003 · **Phase:** PHASE-01, PHASE-13 · **Validation status:** Not run
- **Preconditions:** Lab with the isolated mod set; a lab save S1 with career data.
- **Procedure:** 1) Disable the mod; load S1; play, including demolishing a building the career data references; save as S2. 2) Re-enable the mod; load S2. 3) Load S1.
- **Expected result:** S2 loads with career data in the state SPEC-SAVE defines for this case (carried over or absent), with no corruption. References are revalidated, and the demolished building leads to a fallback. S1 still loads with its own career data. I1–I5 hold.

#### TEST-SAVE-109 — 30-cycle save/load soak (PHASE-12 proposal)
- **Layer:** Integration · **Requirement:** REQ-SAVE-001 – 005 · **Phase:** PHASE-12 · **Validation status:** Not run
- **Preconditions:** Career lab on representative cities; ledger, registry, and persistence readouts.
- **Procedure:** 1) Run 30 cycles of save → leave the city → load. 2) Mix in-session loads and full restarts. 3) Between cycles, vary the activity (missions, purchases, company time, mode switches). 4) Check I1–I6 after each load.
- **Expected result:** **[Proposal]** 30 consecutive cycles with every invariant holding. Any failure is recorded with its cycle number. Counting rules are in [TEST_STRATEGY](TEST_STRATEGY.md) §8.

#### TEST-SAVE-110 — Save and load in every mission and leg state, all careers
- **Layer:** Logic + Integration · **Requirement:** REQ-SAVE-005, REQ-CAREER-004 · **Phase:** PHASE-06, PHASE-08, PHASE-12 · **Validation status:** Not run
- **Preconditions:** Logic harness; Career lab with taxi, delivery, freight, and bus careers.
- **Procedure:** 1) Logic: serialize and deserialize a mission in every lifecycle and leg state and compare. 2) In-game: for each career, save and load in `Offered`, `Accepted`, each leg state (`Approaching`, `Servicing`, `Done`), and just before and just after settlement.
- **Expected result:** Every state round-trips or resolves as SPEC-SAVE / SPEC-MISSION define. Each terminal outcome settles exactly once. No mission object is lost or duplicated.

#### TEST-SAVE-111 — Termination between the career write and the city-save write
- **Layer:** Integration · **Requirement:** REQ-SAVE-001, REQ-SAVE-004 · **Phase:** PHASE-01 · **Validation status:** Not run
- **Preconditions:** Career lab; an owner-approved method to terminate at this point (OPEN-506). For In-save storage, the equivalent point is after our data is handed to the game's save but before the city save completes.
- **Procedure:** 1) Save state A. 2) Earn a reward (state B). 3) Start a save and terminate after the career data is written but before the city save completes. 4) Restart and load the most recent loadable city save. 5) Replay the rewarded mission in that timeline.
- **Expected result:** The career data shown matches the city save actually loaded (state A). B's money never appears. Replaying the mission in A's timeline settles once. Any orphaned newer record is retained or quarantined as SPEC-SAVE defines, never applied to A.

#### TEST-SAVE-112 — Cross-city and cross-profile isolation
- **Layer:** Integration · **Requirement:** REQ-SAVE-001 · **Phase:** PHASE-01, PHASE-07 · **Validation status:** Not run
- **Preconditions:** Lab with two lab cities, including two cities with the same display name; a career profile in each.
- **Procedure:** 1) Earn money, buy a vehicle, and progress in city X. 2) Load city Y and inspect. 3) Load the same-name city and inspect. 4) If SPEC-SAVE supports several profiles in one city, repeat with a second profile.
- **Expected result:** No data from city X appears in any other city or profile. Same-name cities do not collide. I1 holds.

#### TEST-SAVE-113 — Saving during transitions, overlays, and Recovery
- **Layer:** Integration · **Requirement:** REQ-SAVE-005, REQ-ENTITY-003 · **Phase:** PHASE-05, PHASE-06 · **Validation status:** Not run
- **Preconditions:** Career lab; state-trace and registry readouts.
- **Procedure:** Try to save while in `EnteringVehicle`, `ExitingVehicle`, `Recovery`, `Driving` (moving), and with the menu open, using every save path the game offers in character mode. Load each save.
- **Expected result:** Each save captures a stable state as SPEC-SAVE / SPEC-CONTROL define (for example, deferred until a stable state, or normalized). After loading, the avatar and vehicle are at valid positions, and no entity is duplicated.

#### TEST-SAVE-114 — Long session of at least two hours with periodic saves (PHASE-12 proposal)
- **Layer:** Integration + In-game · **Requirement:** REQ-SAVE-001 – 005 · **Phase:** PHASE-12 · **Validation status:** Not run
- **Preconditions:** Career lab on a representative city; ledger and persistence readouts; TEST-PERF-107 running in parallel if possible.
- **Procedure:** 1) Play continuously for at least two hours: careers, mode switches, city edits, and periodic manual saves. 2) Keep an activity log. 3) At the end, save, restart, load, and reconcile the ledger with the log. 4) Record the career record size at each save.
- **Expected result:** **[Proposal]** The invariants hold at every save and after the final load. The ledger matches the activity log. Career record size grows only as SPEC-SAVE expects.

#### TEST-SAVE-115 — Automatic game saves during character mode
- **Layer:** Integration · **Requirement:** REQ-SAVE-001, REQ-SAVE-005 · **Phase:** PHASE-01, PHASE-06 · **Validation status:** Not run
- **Preconditions:** Career lab. **[Unverified]** Whether and how the installed game saves automatically is not known; it must be observed first (TASK-0001 or PHASE-01). If the game has no automatic saves, the run records "not applicable".
- **Procedure:** 1) Enable automatic saves at the shortest interval offered. 2) Play in character mode with an active mission across several automatic saves, including during transitions. 3) Load each automatic save.
- **Expected result:** Every automatic save satisfies the invariants like a manual save. Automatic saves during transitions behave as in TEST-SAVE-113.
